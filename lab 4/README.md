# Лабораторная работа 4

## Тема
Apache Cassandra: LWT, Paxos, конкуренция условных записей и поведение при отказах узлов.

## Цель
Развернуть кластер Cassandra из трех узлов и экспериментально показать:
  1. работу masterless / multi-master архитектуры Cassandra;
  2. отличие обычных записей от LWT-записей;
  3. конфликт Paxos-раундов при конкурентных условных обновлениях одной строки;
  4. необходимость quorum для LWT при отказах узлов.

## Окружение
- СУБД: Apache Cassandra 5, Docker-образ `cassandra:5.0`;
- способ развертывания: Docker Compose;
- количество узлов: 3;
- узлы: `cassandra-1`, `cassandra-2`, `cassandra-3`;
- datacenter: `dc1`;
- replication factor: 3.

## Выполненние
### Этап 1. Развертывание кластера и первая LWT-запись
  1. Разверните кластер из 3-х узлов (cassandra-1, cassandra-2, cassandra-3). Создайте таблицу reservations (room_id int PRIMARY KEY, guest_name text). 
  2. Выполните пробную запись: INSERT ... IF NOT EXISTS. 
  3. Убедитесь, что все узлы синхронизированы. 

### Этап 2. Конкурентные LWT-обновления
  1. Напишите простой скрипт (или запустите несколько параллельных команд), которые пытаются одновременно обновить одну и ту же запись через UPDATE ... SET guest_name = 'X' IF guest_name = 'Y'.
  2. Замерьте время выполнения операций при конкуренции.
  3. Покажите, что Paxos-раунды начинают конфликтовать.

### Этап 3. Сравнение обычных записей и LWT-записей
  1. Выполните 1000 обычных записей в разные строки.
  2. Выполните 1000 LWT-записей в те же строки.
  3. Сравните показатели через nodetool proxyhistograms для Write Latency и CAS Write Latency и делайте выводы.

### Этап 4. Отказы узлов и quorum
  1. Выключите 1 узел из 3-х. Попробуйте выполнить LWT запрос.
  2. Выключите еще один узел (остался 1 живой). Попробуйте снова.
  3. На основе логов объясните, почему LWT требует Quorum на этапе согласования (Paxos)?
